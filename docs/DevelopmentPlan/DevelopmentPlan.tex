To ensure the team works collaboratively and effectively, we have defined unique roles for each member. Each role has its own clearly

\begin{itemize}

\section{Workflow Plan}

Stakeholders and developers will work closely together on creating this project. Thus, it is cruicial to use a workflow that simplifies the development cycle, allows for rapid feedback from stakeholders, and allows for quick iterations on the product. The quicker developers are allowed to iterate, the faster they can tune the product to stakeholder needs. 

The workflow selected for this project is the GitHub workflow due to its simplicity and efficiency. The GitHub workflow dictates that each feature branch will be merged directly into the main branch, and product releases will come from the main branch. Overhead branches are not required for the GitHub workflow, minimizing the amount of branch management a developer has to do. Production releases can be created quickly after each feature branch is merged, thus allowing for rapid feedback from stakeholders and allowing developers to make quick, iterative changes to make stakeholders happy. 

For traceability, GitHub issues created with GitHub Projects will be used to track each feature. A developer will assign themselves to an issue on the project board and create a feature branch to work on it. Once a feature branch is ready to be merged into the main branch, the developer assigned to the issue will create a pull request. For each issue, at least one other team member must review it before approval is given to merge the associated feature branch into the main branch. Once the feature branch is merged, the developer assigned to the issue must close it and set its status to "done." Preferably, each pull request should contain a maximum of 500 changes to lines of code to minimize the workload on reviewers for each individual pull request. 

Lastly, GitHub Actions will be used to create a pipeline for continuous integration and continuous development. An automatic runner for format checking, unit testing, and vulnerability checking will be part of the pipeline. Since the project is using a model that requires training and/or fine-tuning, benchmark testing, regression testing, and model latency checks will also need to be added to the pipeline to ensure thresholds for the product are met. Other checks may be added to the pipeline as needed.

\section{Proof of Concept Demonstration Plan}

At a high level, this application will listen to child speech, process it into its phonetic representation, and analyze this to give feedback to SLPs. The greatest risks associated with this lie in the intermediate audio processing stage:

\begin{enumerate}
  \item \textbf{Converting Child Speech To Phonetic Representation -} Since children are in a developmental phase, their speech patterns vary significantly when compared to adults. Therefore, it may be challenging to ensure an acceptable accuracy rate when converting child speech into phonetic representations.
  \item \textbf{Ensuring An Acceptable Processing Time -} For this application to be viable in a clinical setting, it will need to give real time feedback to the SLP during an appointment on their computers. As per the project supervisors, existing child speech interpretation models are quite slow, so it may be difficult for this one to process the data fast enough to give the clinician feedback in less time than it would have taken for them to reach a deduction themself.
\end{enumerate}

\indent To ensure these risks can be overcome, a suitable training dataset must be found online. To ensure speech to phonetic conversion accuracy, there must be sufficient data to properly train the model. It is important to note that this data must be publicly available to comply with PHIPA patient confidentiality guidelines. 

\indent Once this data is sourced, we will need to develop the actual model that takes child speech and converts it into a readable format with the corresponding phoneme representations. If this model meets the established accuracy benchmarks, it will be feasible to continue designing this application for pediatric speech purposes. Moreover, it is fair to assume that speech therapy offices will use typical office computers that are not equipped with powerful hardware. Therefore, it is necessary to show that the model can meet the benchmark processing time on a device of similar specifications.

\subsection{Languages and Constraints}

\begin{itemize}
\item \textbf{Python}: speech processing, model evaluation and training, and application backend.

\subsection{Libraries and Frameworks}

\begin{itemize}
\item \textbf{Backend}: an Python web framework (e.g., FastAPI)
  with data validation (e.g., Pydantic).
\item \textbf{Frontend}: a JavaScript framework (e.g., React), an API to capture audio from the browser.
\item \textbf{Data}: a relational database (e.g., PostgreSQL) with row-level access control, hosted or self-hosted. 
\item \textbf{Speech and machine learning}: PyTorch, the Hugging Face
  Transformers library, and standard audio-processing libraries.
\end{itemize}

\subsection{Pre-trained Models and Training}

\begin{itemize}
\item We expect to start from pre-trained speech models (e.g., wav2vec2) and existing phone recognizers, to train a model, if the existing solutions are found to not be good enough.
\item Training data will be publicly available child-speech corpora with phonetic annotations
\item Both existing commercial and open-source models are evaluated and are a fallback if a trained model does not meet the agreed targets
\end{itemize}

\paragraph{Components we expect to implement ourselves.}
\begin{itemize}
\item comparison of recognized phones against the target sound
\item an evaluation harness for accuracy, speed, and regression testing
\item the application: practice interface, curriculum, and clinician dashboard.
\end{itemize}

\subsection{Development Tooling}

\begin{itemize}
\item \textbf{Linting and formatting}: Ruff for Python; Prettier for JavaScript.
\item \textbf{Unit testing}: pytest for Python; Vitest for JavaScript.
\item \textbf{Continuous Integration}: Pull requests must have a reviewer; branch protection blocking tests that fail; unit testing to prevent breaking the application on code that compiles on merge;
\end{itemize}

\subsection{Performance Measurement}

\begin{itemize}
\item \textbf{Accuracy}: phone error rate against reference transcriptions;
  precision and recall of substitution detection per target sound; agreement
  with speech-language pathologist annotations.
\item \textbf{Speed}: real-time factor (processing time divided by audio
  duration) and end-to-end latency, measure at each model's size to map the accuracy-versus-latency tradeoff.
\item \textbf{Regression testing}: a fixed held-out evaluation set is re-run after every training run or model change, and a change is accepted only if results stay within agreed thresholds.
\end{itemize}

\subsection{Areas Requiring Additional Training}

\begin{itemize}
\item Phonetics and speech sound disorders, with our SLP advisor.
\item Fine-tuning and evaluating speech models.
\item Database access-control design.
\end{itemize}

\section*{Appendix --- Reflection}

\input{../Reflection.text}

\begin{enumerate}
    \item Why is it important to create a development plan prior to starting the
    project? \\ \\
    Much of the lost time in any project, especially a group project, is due to disorganization and poor coordination.
    Developing that organizational framework ensures that the team is on track to complete the project in a timely manner.
    The value of development planning rather than jumping straight into the code, is ensuring that more of the thinking is done sooner.
    The later work is instead coordinated implementation. Communication is one of the most challenging parts of engineering.
    We can ensure that we all know our expectations of the project, and we can resolve miscommunication early on.
    \item In your opinion, what are the advantages and disadvantages of using
    CI/CD? \\ \\
    CI/CD automates much of the menial labour in software development.
    This lets the team focus on more critical aspects of the work instead of getting bogged down by the friction of testing and deployment.
    It is also a significant time saver.
    Many mistakes, which may be missed by human reviewers, will be caught by the CI/CD pipeline.
    This means reviewers can focus on architectural and design details as opposed to spending time on trivial things, such as naming conventions. \\
    On the other hand, the main disadvantage of implementing CI/CD is the initial time spent setting it up.
    This is especially true for us, since none of us have implemented CI/CD in our own projects, even though we may have worked in codebases that had CI/CD pipelines during our co-ops.
    Spending too much time on the perfect CI/CD pipeline is time lost on the features of the project. 
    \item What disagreements did your group have in this deliverable, if any,
    and how did you resolve them? \\ \\
    We had some disagreements on the Expected Technology section, specifically about the use of Cloud-based and web solutions for our project.
    This project will likely require storing and analyzing the user's medical data, which means we need to consider the ethics and security of our solution.
    Any web-based application would require considering cybersecurity, and any Cloud-based databases would require detailed inspections of the provider's security and privacy policies.
    However, these approaches would significantly ease the technical development of our project, allowing us to focus on meeting our goals.
    We had to spend some time considering the trade-offs of each approach and come to a compromise to move on to other aspects.
\end{enumerate}

\section*{Appendix --- Team Charter}

\subsection*{External Goals}

The team's goals for this project revolve around how useful our product will be to stakeholders. By the end of the capstone, Ghoti is hoping to have created a tool that its supervisors and stakeholders will be using and experimenting with in their labs and clinics. Ghoti also hopes that if the product is trusted, it will be an asset for team members to acquire future employment and bode well for final grades in the capstone course. 

\subsection*{Attendance}

\subsubsection*{Expectations}

Team members are expected to attend all meetings at assigned times. Meetings are booked solidly in advance every Thursday from 3:30pm to 4:30pm. If no cancellations or prior exceptions have been given, all members are expected to attend. 

\subsubsection*{Acceptable Excuse}

Acceptable excuses for missing meetings: 

\begin{itemize}
  \item Family/personal issues or events 
  \item Personal events (given 1-3 days' notice depending on the current capstone situation) 
  \item Personal happenings with school (e.g., midterms, group assignment meetings, etc.) (Must be given 1-3 days' notice depending on the current capstone situation)
\end{itemize}

Should a team member have anything that is required for them to contribute to in a meeting, they should contribute as much as they're able to before they miss the meeting. 

Acceptable excuses for missing deadlines 
\begin{itemize}
  \item Family/personal issues or events 
  \item Personal happenings involving school (e.g., midterms, group assignment meetings, etc.) (Should notify the group ASAP if you realize you are going to miss a deadline due to any school factors). 
\end{itemize}

Missing one deadline is not the end of the world; missing numerous is a pattern and will be considered a problem that will need to be brought up with Dr. Smith. Team members should reach out as early as possible if they realize they are going to miss a deadline so the team can act quickly to help. 
\subsubsection*{In Case of Emergency}

\begin{itemize}
  \item Miss a meeting: Team members should contribute as much as they can before the meeting; if required, team members will designate work assigned in the meeting to the missing member and will notify them of this once the meeting is finished. 
  \item Can't meet a deliverable: Team members should contribute what they can but let the team know of the situation ASAP. The team will reassign work to complete the deliverable on time. Life happens, but poor communication or repeated failures may involve team discussion or discussions with Dr. Smith. 
\end{itemize}

\subsection*{Accountability and Teamwork}

\subsubsection*{Quality} 
\begin{itemize}
  \item Quality of Team Meetings: Team members are expected to show up with a general idea of what will be on the agenda for any given meeting. If there is any material or information team members need to have prepared before the meeting, they are expected to be prepared with said materials. Should a team member find themselves unable to properly prepare for a meeting, they should notify their team members as soon as possible and work with the team to find a solution. Situations like these can be forgiven as long as they are communicated ahead of time and not part of a greater pattern of failing to deliver. If a team member is assigned to take meeting notes, the notes should be concise and cover all key discussion points. 
  \item Quality of Deliverables: Each team member should complete their assigned portions of deliverables (barring accepted excuses), focusing as much as they can on producing quality work. Deliverables should be reviewed by each team member, and inconsistencies/issues should be brought up with the individual(s) responsible for creating them. Team meetings or discussions may be needed if the inconsistencies/issues are contested topics that cannot be resolved solely by the involved parties.  
\end{itemize}
\subsubsection*{Attitude}

Each team member should bring the attitude of wanting the team to succeed in the goals it set out to achieve. The actions that team members take should be meant to uplift the project and team as a whole and not tear each other down. Specifics are found in our code of conduct and conflict resolution plan: 
\begin{itemize}
  \item Code of Conduct: 
  \begin{itemize}
    \item Team members should treat each other with respect and dignity. No personal attacks or insults are allowed in team discussions. 
    \item Having fun/joking around is fine as long as it doesn't degrade the quality of a meeting or cause discomfort in team members. 
    \item Team members should communicate quickly and often; the quicker issues are communicated, the quicker they can be resolved. 
  \end{itemize}
  \item Conflict Resolution Plan: 
  \begin{itemize}
    \item Issues between team members should be discussed individually first; calling each other out in team meetings shouldn't be the go-to method of discussing issues unless it is warranted.
    \item Should no resolution be found between individuals, conflicts will be raised to the team level for discussion.
    \item Should team discussions fail, the issue will be brought to the TAs/Prof for resolution.
    \item Conflicts of a serious or harmful nature should be directly brought up to the professor for the safety of the parties involved.
  \end{itemize}
\end{itemize}

The team will use tentative deadlines to keep each other on track for team deliverables. During team meetings, we will discuss current progress, roadblocks, and upcoming deadlines to ensure everyone is on the same page with the work they have been assigned. A team member who is confused about the work expected from them should immediately reach out to the group for clarification. Team wins should be recognized throughout the capstone project's development, and shoutouts should be given to team members who are doing well in their work. If there are team members who are performing below expectations, the team should come together to address the issues hindering them. If necessary, a plan should be made for the team member that outlines steps for improvement. Should a team member fail to meet two deadlines for project deliverables, frequent or daily check-ins will be required to keep them on track and monitor their progress. Should failures to meet project deliverables continue, discussions with the Dr. Smith will be arranged for next steps.

Below 50\%, a meeting with the TA will be arranged. Below 30\%, a meeting with Dr. Smith will be arranged. 
 
The team will divide work equally as it relates to GitHub issues. If everyone is doing their assigned share of GitHub issues, it will be considered as the work being equally shared. If the team finds out that there is an unfair balance of work given to a team member, the team will reconvene to redistribute tasks.
