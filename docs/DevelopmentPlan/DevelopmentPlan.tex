\subsection{Languages and Constraints}

\begin{itemize}
\item \textbf{Python}: speech processing, model evaluation and training, and application backend.
\item \textbf{JavaScript:} user interface.
\item \textbf{SQL:} data storage and access control.
\item \textbf{Git, GitHub, and GitHub Projects:} course requirements and will be used for version control, issue tracking, code review, and planning.
\item The application is web-based so it will run on devices that a typical clinic would have, i.e. a desktop.
\end{itemize}

\subsection{Libraries and Frameworks}

\begin{itemize}
\item \textbf{Backend}: an Python web framework (e.g., FastAPI)
  with data validation (e.g., Pydantic).
\item \textbf{Frontend}: a JavaScript framework (e.g., React), an API to capture audio from the browser.
\item \textbf{Data}: a relational database (e.g., PostgreSQL) with row-level access control, hosted or self-hosted. 
\item \textbf{Speech and machine learning}: PyTorch, the Hugging Face
  Transformers library, and standard audio-processing libraries.
\end{itemize}

\subsection{Pre-trained Models and Training}

\begin{itemize}
\item We expect to start from pre-trained speech models (e.g., wav2vec2) and existing phone recognizers, to train a model, if the existing solutions are found to not be good enough.
\item Training data will be publicly available child-speech corpora with phonetic annotations
\item Both existing commercial and open-source models are evaluated and are a fallback if a trained model does not meet the agreed targets
\end{itemize}

\paragraph{Components we expect to implement ourselves.}
\begin{itemize}
\item comparison of recognized phones against the target sound
\item an evaluation harness for accuracy, speed, and regression testing
\item the application: practice interface, curriculum, and clinician dashboard.
\end{itemize}

\subsection{Development Tooling}

\begin{itemize}
\item \textbf{Linting and formatting}: Ruff for Python; Prettier for JavaScript.
\item \textbf{Unit testing}: pytest for Python; Vitest for JavaScript.
\item \textbf{Continuous Integration}: Pull requests must have a reviewer; branch protection blocking tests that fail; unit testing to prevent breaking the application on code that compiles on merge;
\end{itemize}

\subsection{Performance Measurement}

\begin{itemize}
\item \textbf{Accuracy}: phone error rate against reference transcriptions;
  precision and recall of substitution detection per target sound; agreement
  with speech-language pathologist annotations.
\item \textbf{Speed}: real-time factor (processing time divided by audio
  duration) and end-to-end latency, measure at each model's size to map the accuracy-versus-latency tradeoff.
\item \textbf{Regression testing}: a fixed held-out evaluation set is re-run after every training run or model change, and a change is accepted only if results stay within agreed thresholds.
\end{itemize}

\subsection{Areas Requiring Additional Training}

\begin{itemize}
\item Phonetics and speech sound disorders, with our SLP advisor.
\item Fine-tuning and evaluating speech models.
\item Database access-control design.
\end{itemize}

\section{Use of AI and LLMs}

Our team will use LLMs to support brainstorming, application development, and documentation. Tools such as Claude and ChatGPT may be used to explore design approaches, explain concepts, and  write code. In the coding process, agents will also be implemented to improve workflow and follow best practices. Team members will make and take responsibility for all project decisions and submitted work.

We will review any generated code before including it in the application. We will check that it meets the project requirements, follows our design, and works as intended by running relevant builds, checks, and tests. Any output that cannot be verified or does not meet these checks will be revised or discarded.
