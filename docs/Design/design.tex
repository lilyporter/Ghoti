\section{Introduction}

Decomposing a system into modules is a commonly accepted approach to developing
software.  A module is a work assignment for a programmer or programming
team~\citep{ParnasEtAl1984}.  We advocate a decomposition
based on the principle of information hiding~\citep{Parnas1972a}.  This
principle supports design for change, because the ``secrets'' that each module
hides represent likely future changes.  Design for change is valuable in SC,
where modifications are frequent, especially during initial development as the
solution space is explored.

Our design follows the rules layed out by \citet{ParnasEtAl1984}, as follows:
\begin{itemize}
\item System details that are likely to change independently should be the
  secrets of separate modules.
\item Each data structure is implemented in only one module.
\item Any other program that requires information stored in a module's data
  structures must obtain it by calling access programs belonging to that module.
\end{itemize}
After completing the first stage of the design, the Software Requirements
Specification (SRS), the Module Guide (MG) is developed~\citep{ParnasEtAl1984}.
In specific, this document describes the software architecture and detailed module
interfaces for PronouncedFish: an assistive tool designed to 
aid SLPs in their daily workflow. It provides an interface for SLPs to manage 
their appointments, patients, and offer complementary insights by listening in on sessions. The full documentation and implementation can be found at \href{https://github.com/lilyporter/Ghoti/tree/main/}{this repository}. The MG
specifies the modular structure of the system and is intended to allow both
designers and maintainers to easily identify the parts of the software.  The
potential readers of this document are as follows:

\begin{itemize}
\item New project members: This document can be a guide for a new project member
  to easily understand the overall structure and quickly find the
  relevant modules they are searching for.
\item Maintainers: The hierarchical structure of the module guide improves the
  maintainers' understanding when they need to make changes to the system. It is
  important for a maintainer to update the relevant sections of the document
  after changes have been made.
\item Designers: Once the module guide has been written, it can be used to
  check for consistency, feasibility, and flexibility. Designers can verify the
  system in various ways, such as consistency among modules, feasibility of the
  decomposition, and flexibility of the design.
\end{itemize}

Part~\ref{part:architecture} describes the anticipated and unlikely changes,
module hierarchy and dependencies, module responsibilities, and traceability
from requirements and anticipated changes to modules.
Part~\ref{part:detailed} defines shared notation and types, followed by the
module interface specifications.

\section{Anticipated and Unlikely Changes} \label{SecChange}

This section lists possible changes to the system. According to the likeliness
of the change, the possible changes are classified into two
categories. Anticipated changes are listed in Section \ref{SecAchange}, and
unlikely changes are listed in Section \ref{SecUchange}.

\subsection{Anticipated Changes} \label{SecAchange}

Anticipated changes are the source of the information that is to be hidden
inside the modules. Ideally, changing one of the anticipated changes will only
require changing the one module that hides the associated decision. The approach
adapted here is called design for
change.

\begin{description}
\item[\refstepcounter{acnum} \actheacnum \label{acHardware}:] The specific
  hardware on which the software is running, including the tablet or computer
  model and its microphone and audio capture hardware.
\item[\refstepcounter{acnum} \actheacnum \label{acInput}:] The format of the
  audio input data (e.g., sample rate, bit depth, encoding, and file container).
\item[\refstepcounter{acnum} \actheacnum \label{acModel}:] The speech
  recognition and phoneme analysis model (e.g., moving from one pre-trained
  wav2vec2 variant to another, or to a different architecture or framework).
\item[\refstepcounter{acnum} \actheacnum \label{acPhonemeSet}:] The phoneme
  inventory and the representation of phonemes (e.g., IPA symbols, ARPAbet, or
  feature vectors) used to compare expected and recognized speech.
\item[\refstepcounter{acnum} \actheacnum \label{acErrorTypes}:] The set of
  speech error patterns detected. The system currently targets substitution
  errors, and may later be extended to omissions, distortions, or other
  patterns.
\item[\refstepcounter{acnum} \actheacnum \label{acPopulation}:] The target
  population and language, such as the age range (currently 4--6), and
  dialect or language (currently monolingual North American English).
\item[\refstepcounter{acnum} \actheacnum \label{acPractice}:] The content and
  structure of practice activities, including the word lists, lesson
  suggestion rules, and difficulty progression.
\item[\refstepcounter{acnum} \actheacnum \label{acScoring}:] The algorithm for
  scoring pronunciation and computing per-phoneme confidence.
\item[\refstepcounter{acnum} \actheacnum \label{acVisual}:] The format and
  presentation of results, progress charts, and exported reports.
\item[\refstepcounter{acnum} \actheacnum \label{acUI}:] The user interface
  framework and layout, including support for new device form factors and a
  future patient-facing, homework, or mobile interface.
\item[\refstepcounter{acnum} \actheacnum \label{acDB}:] The database
  technology and schema used to persist session, patient, and progress data.
\item[\refstepcounter{acnum} \actheacnum \label{acAuth}:] The authentication
  and authorization mechanism (e.g., password policy, two-factor method,
  consent-code scheme, and identity provider).
\item[\refstepcounter{acnum} \actheacnum \label{acAudit}:] The audit trail
  format and the data retention and backup policies.
\item[\refstepcounter{acnum} \actheacnum \label{acDeploy}:] The hosting and
  deployment environment (e.g., cloud provider, containerization, and
  CI/CD pipeline).
\item[\refstepcounter{acnum} \actheacnum \label{acPrivacy}:] Privacy and
  regulatory requirements, such as amendments to PHIPA or the need to meet
  additional jurisdictions' regulations.
\end{description}

\subsection{Unlikely Changes} \label{SecUchange}

The module design should be as general as possible. However, a general system is
more complex. Sometimes this complexity is not necessary. Fixing some design
decisions at the system architecture stage can simplify the software design. If
these decision should later need to be changed, then many parts of the design
will potentially need to be modified. Hence, it is not intended that these
decisions will be changed.

\begin{description}
\item[\refstepcounter{ucnum} \uctheucnum \label{ucIO}:] Input/Output devices
  (Input: microphone audio and keyboard/touch, Output: screen display and
  audio playback; Memory and database for persistence).
\item[\refstepcounter{ucnum} \uctheucnum \label{ucAssistive}:] The assistive
  role of the system. It will always support, and never replace, the clinical
  judgment of the speech-language pathologist.
\item[\refstepcounter{ucnum} \uctheucnum \label{ucArch}:] The web-based
  client--server architecture of the system.
\item[\refstepcounter{ucnum} \uctheucnum \label{ucAudioModality}:] Speech audio
  as the primary input modality, with analysis at the phoneme level.
\item[\refstepcounter{ucnum} \uctheucnum \label{ucUsers}:] The primary user
  roles of speech-language pathologist and patient, with SLP-led sessions as
  the core workflow.
\item[\refstepcounter{ucnum} \uctheucnum \label{ucLicense}:] The open-source
  GPL licensing of the software.
\item[\refstepcounter{ucnum} \uctheucnum \label{ucPHIPA}:] The requirement to
  comply with PHIPA for handling personal health information.
\end{description}

\section{Use Hierarchy Between Modules} \label{SecUse}

In this section, the uses hierarchy between modules is
provided. \citet{Parnas1978} said of two programs A and B that A {\em uses} B if
correct execution of B may be necessary for A to complete the task described in
its specification. That is, A {\em uses} B if there exist situations in which
the correct functioning of A depends upon the availability of a correct
implementation of B.  Figure \ref{FigUH} illustrates the use relation between
the modules. It can be seen that the graph is a directed acyclic graph
(DAG). Each level of the hierarchy offers a testable and usable subset of the
system, and modules in the higher level of the hierarchy are essentially simpler
because they use modules from the lower levels.

\section{Module Decomposition} \label{SecMD}

Modules are decomposed according to the principle of ``information hiding''
proposed by \citet{ParnasEtAl1984}. The \emph{Secrets} field in a module
decomposition is a brief statement of the design decision hidden by the
module. The \emph{Services} field specifies \emph{what} the module will do
without documenting \emph{how} to do it. For each module, a suggestion for the
implementing software is given under the \emph{Implemented By} title. If the
entry is \emph{OS}, this means that the module is provided by the operating
system or by standard programming language libraries.  \emph{\progname{}} means the
module will be implemented by the \progname{} software.

Only the leaf modules in the hierarchy have to be implemented. If a dash
(\emph{--}) is shown, this means that the module is not a leaf and will not have
to be implemented.

\subsection{Hardware Hiding Modules}

\subsubsection{Audio Input Adapter Module (\mref{mHH})}

\begin{description}
\item[Secrets:] Device-specific access to microphones and displays.
\item[Services:] Provides microphone access and display output through
browser and operating system interfaces. Audio Capture (\mref{mAudioCapture})
uses the microphone interface to record attempts and handles recording
usability checks and reporting (FR-AC1--3).
\item[Implemented By:] Browser and operating system
\end{description}

\subsection{Behaviour-Hiding Module}

\subsubsection{Audio Capture Module (\mref{mAudioCapture})}

\begin{description}
\item[Secrets:]Hides the audio recording lifecycle. This includes hiding any input audio quality variations by using preprocessing. It also normalizes any differing input file formats. Finally, it ensures that the final audio file is valid for analysis by making quality assurance checks.  
\item[Services:]Provides a fully processed audio file in the exact format that the following speech analysis model expects. It has all metadata needed to make an appropriate deduction. 
\item[Implemented By:] PronouncedFish
\item[Type of Module:] Abstract Object
\end{description}

\subsubsection{Audio Analysis Module (\mref{mAudioAnalysis})}

\begin{description}
\item[Secrets:] The algorithms and models used to convert recorded speech into
  a phoneme-level assessment. This includes the machine learning model used to
  recognize phonemes, the method for determining a phoneme's placement within
  a word, the representation of phonemes as articulatory feature vectors, and
  the distance metric used to compare recognized phonemes with expected ones.
\item[Services:] Accepts a recorded audio attempt and the expected word or
  phoneme sequence, and returns a phonemic analysis of the attempt. It
  performs the following steps:
  \begin{itemize}
  \item Recognizes the sequence of phonemes in the audio using a pre-trained (Pasketti Challenge)
    ML phoneme recognition model.
  \item Identifies the placement of each phoneme within the word (initial,
    medial, or final).
  \item Represents each recognized and expected phoneme as a feature vector
    using the PanPhon library.
  \item Computes the Manhattan distance between the recognized and expected
    phoneme vectors to quantify how far each attempt is from the target, which
    identifies substitution errors (e.g., ``rabbit'' $\rightarrow$
    ``wabbit'').
  \end{itemize}
  The resulting phoneme-level results (recognized phoneme, expected phoneme,
  placement, distance, and confidence) are passed to the results and progress
  modules. The output is intended to assist, and never replace, the clinical
  judgment of the speech-language pathologist.
\item[Implemented By:] Python (PyTorch/Hugging Face model, PanPhon library)
\item[Type of Module:] Abstract Object
\end{description}

\subsubsection{Etc.}

\subsubsection{Session Management (\mref{mSessionManagement})}

\begin{description}
\item[Secrets:] The session state information (Prompt, analysis, continue, redo), 
How temporary session data is accumulated before being saved, 
how redos and overrides affect the final data on the completion of a session,
how the session handles the differences in testing and treatment session modes,
how patient consent to audio recordings is handled with data accumulation.
\item[Services:] Manages a clinician-supervised session for a specific patient from setup to completion. 
Offers two different session modes: testing mode for gathering information about the patient’s speech errors (no helps or hints to treat the speech disorder) and treatment mode for providing support to the child while practicing target phonemes (e.g., hints and feedback)(FR-SM3 and FR-DMR11).
Allows the SLP to select the patient, target phonemes, and lesson plans (FR-SM1) (taken from the Practice Items \& Lesson Plans Module (\mref{mPracticeItems})), and to start, repeat, skip, and end attempts as well as the session (FR-SM2 and FR-PAR6). 
Presents image-cue prompts for each item to the child (FR-PAR5) and coordinates Audio Capture (\mref{mAudioCapture}) and Speech Analysis (\mref{mSpeechAnalysis}) for each attempt, surfacing flagged or unclassifiable results so the SLP can retry (FR-AC3 and FR-SA3). 
Records the support level for each attempt (FR-SM3) and applies SLP overrides while retaining the original analysis (FR-SM4). 
Provides current-attempt results and running session counts to the Clinician Dashboard (FR-RDV1, FR-RDV4, and FR-RDV6).
On completion, submits the session and its attempts to Patient Records \& Progress Tracking (\mref{mPatientRecords}) to be processed and stored, associated only with the session’s patient (FR-DMR6--7). 
Interfaces with the Clinician Dashboard / Results Visualization (\mref{mClinicianDashboard}) to provide current-session information (FR-RDV1--9 and FR-HA7).
\item[Implemented By:] PronouncedFish
\item[Type of Module:] Abstract Object
  %[Information to include for leaf modules in the decomposition by secrets tree.]
\end{description}

\subsubsection{Practice Items \& Lesson Plans (\mref{mPracticeItems})}
\begin{description}
\item[Secrets:] The internal representation and organization of the practice-item
catalogue and saved lesson plans, including the associations between each
practice item, its target speech challenge, target phoneme(s), word position,
correct word, image cue, and expected IPA transcription. The module also hides
the rules used to assemble, retrieve, and maintain reusable practice items for creating lesson plans.

\item[Services:] Provides the SLP with ability to create, view, modify, and
delete system practice items. Each practice item is associated with one or more target
speech challenges and a relevant word position. Each item includes the correct
word, an image cue, and its expected IPA transcription. The module provides
access to practice items by target phoneme and word position (FR-PAR1 and
FR-PAR3). The system baseline catalogue provides at least three practice items for each
supported target phoneme in each supported word position, using words from a
standardized set that are appropriate for the intended age range (FR-PAR2 and
FR-PAR4).

The module also supports the creation viewing, editing, and deleting of saved
lesson plans by allowing the SLP to select practice items from the catalogue.
A saved lesson plan can be selected and assigned to a patient session. 

The module provides the selected lesson plan and its practice-item content to
Session Management (\mref{mSessionManagement}) for use during a session.

\item[Implemented By:] PronouncedFish
\item[Type of Module:] Abstract Object
\end{description}

\subsubsection{Patient Records \& Progress Tracking (\mref{mPatientRecords})}

See Section~\ref{mis:records} for the detailed interface specification.

\begin{description}
\item[Secrets:] The organization of the patient record, including
how completed sessions are associated with the patient and how progress is

\item[Services:] Maintains patient records and provides authorized retrieval and
export of session history, including all three speech error types. Provides
per-target-phoneme performance over time, between-session comparisons,

and allows authorized users to retrieve and copy the audit trail

\item[Implemented By:] PronouncedFish
\item[Type of Module:] Abstract Object
\end{description}

\subsubsection{Clinician Dashboard / Results Visualization (\mref{mClinicianDashboard})}

See Section~\ref{mis:dashboard} for the detailed interface specification.

\begin{description}
\item[Secrets:] The presentation rules for clinician-facing speech results.
\item[Services:] Presents expected and recognized phonemes in IPA and shows
each identified substitution, omission, and addition in its word position or
insertion location. Displays counts by error type and current-session
correct and incorrect counts, with independent and cued counts for correct

The heat map normalizes the SRS Manhattan distance over phonological feature
vectors to a closeness scale from zero to one. Gaps receive no score.
\item[Implemented By:] PronouncedFish
\item[Type of Module:] Abstract Data Type (one view instance per clinician
dashboard)
\end{description}

\section{Connection Between Requirements and Design} \label{SecConnection}

The design of the system is intended to satisfy the requirements developed in
the SRS. In this stage, the system is decomposed into modules. The connection
between requirements and modules is listed in Table~\ref{TblRT}. Several
requirements leave room for interpretation, and some design needs go beyond
the SRS. Rather than leave these decisions implicit, each is recorded below
with the requirements it responds to, the decision made, the reason, and the
module that carries it out.

\paragraph{Speech error scope.}
\emph{Requirements:} FR-SA1, FR-RDV2--3, NFR-MAI2.\\
\emph{Assumptions:} A6.\\
\emph{Theoretical Methods:} TM1, TM2.\\
\emph{Decision:} Phase 1 supports substitutions, omissions, and additions.
Speech Analysis compares recognized IPA with the expected pronunciation and its
acceptable variants. It reports a substitution when a different phoneme
replaces an expected phoneme, an omission when an expected phoneme is absent,
and an addition when an extra phoneme occurs before, between, or after expected
phonemes. This extends the substitution cases in FR-SA1 and FR-RDV2--3.\\
\emph{Rationale:} A6 already assumes that a length mismatch indicates an
omission or addition, and TM2 pairs phonemes by position only when the
sequences have equal length. Reporting the three types lets the SLP see the
cause of a mismatch instead of an unexplained failure. Modelling
\texttt{SpeechError} as a variant type also supports NFR-MAI2.\\
\emph{Modules:} \mref{mSpeechAnalysis}, \mref{mPatientRecords}, \mref{mClinicianDashboard}.

\paragraph{Alignment of recognized and expected phonemes.}
\emph{Requirements:} FR-SA1, FR-SA2.\\
\emph{Assumptions:} A3, A4, A6. \\
\emph{Theoretical Models:} TM1, TM2. \\
\emph{Decision:} Speech Analysis aligns the recognized sequence with the
expected sequence before classifying differences, and produces one observation
for each target occurrence. TM2's position-by-position pairing is the special
case where both sequences have the same length.\\
\emph{Rationale:} Positional pairing cannot locate an omission or addition,
because every later phoneme shifts. Alignment is what makes the insertion
location and word position reportable.\\
\emph{Modules:} \mref{mSpeechAnalysis}.

\paragraph{Acceptable variants.}
\emph{Requirements:} FR-SA2.\\
\emph{Assumptions:} A4.\\
\emph{Decision:} Acceptable variants are applied when classifying every error
type, not only substitutions.\\
\emph{Rationale:} A4 defines variants as per-position sets of substitute
phonemes. An omission or addition that reflects accepted pronunciation would
otherwise be reported as an error.\\
\emph{Modules:} \mref{mSpeechAnalysis}, \mref{mPracticeItems}.

\paragraph{Unclassifiable attempts.}
\emph{Requirements:} FR-SA3, FR-AC3.\\
\emph{Assumptions:} A10.\\
\emph{Decision:} An attempt whose confidence is below the threshold is
classified as unclassifiable. It is shown with any available recognized IPA,
and it is excluded from correct and incorrect counts and from progress until
the SLP resolves it. The threshold value is not fixed by this design, because
it comes from the validation study.\\
\emph{Rationale:} FR-SA3 forbids forcing a classification on poor input.
Excluding such attempts keeps unreliable results out of progress measures.\\
\emph{Modules:} \mref{mSpeechAnalysis}, \mref{mSessionManagement},
 \mref{mPatientRecords}, \mref{mClinicianDashboard}.

\paragraph{SLP overrides and corrections.}
\emph{Requirements:} FR-SM4, FR-DMR3, FR-DMR3.1, FR-RDV7.\\
\emph{Decision:} An attempt-level override sets the effective classification.
The original analysis is always kept and remains visible. The SLP may also
correct individual phoneme observations or error records. Attempt-level
overrides do not change phoneme-level counts.\\
\emph{Rationale:} The SLP's judgement takes precedence, but results remain
auditable. Phoneme counts depend on which phonemes were produced, which an
attempt-level label does not change.\\
\emph{Modules:} \mref{mSessionManagement}, \mref{mPatientRecords}, \mref{mClinicianDashboard}, \mref{mPersistence}.

\paragraph{Support levels.}
\emph{Requirements:} FR-SM3, FR-DMR2, FR-DMR2.1, FR-DMR11, FR-RDV4.\\
\emph{Decision:} The SLP records one or more of the support levels (independent,
semantic cue, repetition or model) used to support a patient for each attempt. For summaries, any correct
attempt that needed a cue counts as cued, attempts that needed a repeat counts as repeated, and attempts that needed no help counts as independent.\\
\emph{Rationale:} FR-RDV4 asks only for an independent versus cued split, while
FR-SM3 and FR-DMR2 ask for the finer levels to be recorded. Storing the fine
level and deriving the split keeps both.\\
\emph{Modules:} \mref{mSessionManagement}, \mref{mPatientRecords}, \mref{mClinicianDashboard}.

\paragraph{Session completion and saving.}
\emph{Requirements:} FR-DMR1, FR-DMR6, FR-DMR7, FR-DMR2, FR-DMR3.\\
\emph{Decision:} Session Management owns the live session. A completed session
and its attempts are saved to Patient Records as a single operation, and a
retry of the same save leaves one stored session. A failed save leaves records
unchanged. Each session belongs to exactly one patient, and each attempt takes
its patient from its session.\\
\emph{Rationale:} Saving everything together or not at all prevents partial
sessions, and the ownership rule enforces FR-DMR7 structurally.\\
\emph{Modules:} \mref{mSessionManagement}, \mref{mPatientRecords},
\mref{mPersistence}.

\paragraph{Auditing and deletion.}
\emph{Requirements:} FR-DMR4, FR-DMR5, NFR-USA2, SLP-R3.\\
\emph{Decision:} Viewing, creating, modifying, exporting, and deleting a record
each create an audit event. If the audit write fails, the operation fails
without exposing data or committing a change. Audit events are append-only and
keep a patient identity reference after the clinical record is deleted.
Deletion requires SLP confirmation and removes the patient, sessions, and
attempts from active records.\\
\emph{Rationale:} Failing when auditing fails guarantees that every access is
recorded. NFR-USA2 allows either confirmation or recovery within 72 hours, and
the design takes confirmation, which keeps deleted data from lingering in a
recoverable state. Retaining the reference lets the delete event remain
traceable.\\
\emph{Modules:} \mref{mPatientRecords}, \mref{mPersistence}.

\section{Design of Communication Protocols}

The system does not use any custom hardware communication protocol. Two
communication paths are described below.

\subsection{Audio Capture}

Audio is captured through the standard browser media interfaces
(\texttt{MediaDevices.getUserMedia} and \texttt{MediaRecorder}), which are
provided by the browser and operating system on the tablet (see \mref{mHH}).
The browser asks the user for microphone permission, and the Audio Input Module
(\mref{mAudioInput}) only begins recording once permission is granted. If
permission is denied or no microphone is available, the failure is reported to
the user and no recording is started. Recordings are encoded in a single fixed
format (e.g., WAV at a fixed sample rate) so that the Audio Analysis Module
(\mref{mAudioAnalysis}) always receives consistent input.

\subsection{Tablet to Server}

The tablet communicates with the server over an HTTPS connection. All data,
including recorded audio, login information, and results, is encrypted in
transit using TLS, and plain HTTP connections are rejected. This supports the
PHIPA compliance requirement for personal health information. The tablet sends
recordings to the server for analysis, and the server returns the phoneme-level
results over the same connection.

\subsection{Shared Interface Types} \label{sec:interface-types}

The following records are shared by the session, records, dashboard, and
persistence interfaces. Each identifier type denotes an opaque identifier
for the named entity. An optional value is either present or absent.

\begin{description}
\item[StoreConfig] Configuration identifying a durable store.
\item[Actor] An authenticated user identity and permissions to act on patient
records or retrieve audit events.
\item[Patient] Patient identifier and identifying information.
\item[SpeechError] A record identifying a word occurrence in the practice
item and one of the following error kinds.
\begin{description}
\item[Substitution] Expected phoneme, produced phoneme, and expected
phoneme position within the word.
\item[Omission] Expected phoneme and its position within the word.
\item[Addition] Extra produced phoneme and its insertion location before,
between, or after expected phonemes. A location is the number of expected
phonemes preceding the insertion in that word. Multiple additions at the
same location retain their recognized order.
\end{description}
\item[Attempt] Attempt identifier, practice item, target phonemes, support
level, original analysis, and optional SLP correction. The analysis contains
expected and recognized IPA sequences (recognized IPA may be absent),
an ordered sequence of SpeechError, confidence when available, and
classification. It also contains an aligned observation
for each target occurrence, with an expected phoneme, optional produced
phoneme, and status (accepted, incorrect, or unclassifiable). The attempt
classification is correct, incorrect, or unclassifiable. An SLP correction
contains the SLP identity, optional correct/incorrect override, and any
phoneme-level corrections to the observations or error records.
\item[Session] Session identifier, patient identifier, SLP identity, session
date, session mode (testing or treatment), targets, practice items, SLP inputs, status (active or completed),
and a sequence of completed attempts. Only a completed snapshot is accepted
by \texttt{saveSession}.
\item[SessionPair] Two distinct session identifiers ordered from baseline
to follow-up.
\item[Progress] For a patient and target phoneme, dated session points
containing session identifiers and eligible, correct, and incorrect target
observations, with cue information where available. Includes an optional
comparison and optional improvement or persistent-error indicators.
\item[AuditEvent] Action, information type, timestamp, actor identity, and
retained patient identity reference.
\item[HistoryExport, AuditCopy] Copies of authorized session history and
audit events, respectively. The export formats are implementation decisions.
\end{description}

\section{MIS of Session Management} \label{mis:session}

\subsection{Module}
SessionManager runs one clinician-supervised practice session for one
patient, from setup to completion. It covers FR-SM1--4 and FR-PAR5--7, and the
session-side parts of FR-AC3, FR-SA3, FR-DMR2--3, FR-DMR6--7, and FR-DMR11.

\subsection{Uses}
Audio Capture supplies a recording and its usability flags (FR-AC1 and FR-AC3). Speech Analysis supplies the analysis of a usable recording (FR-SA1 and FR-SA3). Practice Items \& Lesson Plans supplies items, their target phonemes, and image cues. Patient Records \& Progress Tracking provides patient information if authorized and stores the completed session. Clinician Dashboard / Results Visualization uses this module; this module does not use the Dashboard.

\subsection{Syntax}

\subsubsection{Exported Types}
\begin{description}
\item[SessionMode] Testing or Treatment. Testing gathers information about the
patient's speech with no cues, hints, or modelling. Treatment allows support
from the SLP.
\item[SupportLevel] independent, semantic cue, or repetition/model. The support
a child received for one attempt (FR-SM3 and FR-DMR2.1).
\item[SessionSetup] Patient identifier, SessionMode, target phonemes, and
lesson plan.
\item[Prompt] A practice item and its image cue, presented for an attempt
(FR-PAR5).
\item[AttemptOutcome] Either \emph{flagged}, with the usability reasons from
Audio Capture, or \emph{analysed}, with the resulting Attempt.
\end{description}
Session, Attempt, Actor, and SLP correction are the shared types in
Section~\ref{sec:interface-types}. The Attempt records its SupportLevel.

\subsubsection{Exported Constants}
None.

\subsection{Semantics}

\subsubsection{State Variables}
\begin{itemize}
\item \texttt{session}: the active Session record, or absent. Initially absent.
Its attempts are the retained attempts so far, in order.
\item \texttt{actor}: the Actor who started the session.
\item \texttt{current}: the open attempt, or absent. It holds the practice
item, its SupportLevel (initially independent), and a state: prompted,
flagged, or analysed. An analysed current attempt is also the last element of
\texttt{session}'s attempts.
\item \texttt{nextId}: counter used to give attempts identifiers that are
unique within the session.
\end{itemize}
The session's SessionMode is part of the active Session record.

\subsubsection{Environment Variables}
A clock supplying the session date. The child-facing display, which shows the
Prompt.

\subsubsection{Assumptions}
The caller supplies an authenticated actor. One session is active at a time.
Each attempt is a single spoken target word (SRS A1), and the SLP supervises
the session (SRS A7). Audio Capture and Speech Analysis return the values
described in Section~\ref{sec:interface-types}. Recorded audio is used only
for its attempt (FR-AC2).

\subsubsection{Access Routine Semantics}
Every routine except \texttt{startSession} raises \texttt{Inactive} when no
session is active. Routines that act on the current attempt raise
\texttt{NoAttempt} when \texttt{current} is absent.

\begin{description}
\item[] \texttt{startSession(actor, setup)}\par
Raise \texttt{Conflict} if a session is already active. Confirm access to the
setup's patient identifier through Patient Records \& Progress Tracking;
\texttt{Denied}, \texttt{Missing}, and \texttt{Unavailable} propagate. Raise
\texttt{Invalid} when the target set or item set is empty, when a target is
outside the predetermined substitution list (FR-SM1 and FR-SA1), or when an
item does not exercise at least one selected target. On success, create an
active Session with a new identifier, the patient, the actor's SLP identity,
the setup's SessionMode, the clock date, the targets, the items, no SLP inputs,
and no attempts. Record the actor, clear \texttt{current}, and return the
Session.
\item[] \texttt{startAttempt(item)}\par
Raise \texttt{Invalid} if the item is not in the session's practice items.
Raise \texttt{Busy} if \texttt{current} is prompted or flagged and has not been
repeated or skipped. If \texttt{current} is analysed, it is final and stays in
the session. Set \texttt{current} to a prompted attempt for the item with
independent support, and return the Prompt supplied by Practice Items
(FR-PAR5).
\item[] \texttt{recordAttempt()}\par
Raise \texttt{Unavailable} if Audio Capture or Speech Analysis fails; the state
is unchanged. Obtain a recording from Audio Capture. If the recording is
flagged, set \texttt{current} to flagged, add nothing to the session, and
return flagged (FR-AC3). Otherwise obtain the analysis from Speech Analysis
for the item and its targets. Build an Attempt with a new identifier, the item,
its targets, the SupportLevel of \texttt{current}, and the original analysis,
which may classify it as unclassifiable (FR-SA3). Append it to the session's
attempts, set \texttt{current} to analysed, and return analysed. The Dashboard
sees the new attempt through \texttt{getSnapshot}.
\item[] \texttt{setSupport(level)}\par
Raise \texttt{Invalid} if the level is not in \texttt{allowedSupport(mode)},
where mode is the session's SessionMode. Set the SupportLevel of
\texttt{current}, and of its Attempt when analysed (FR-SM3 and FR-DMR2). The
SLP may call this before or after \texttt{recordAttempt}.
\item[] \texttt{repeatAttempt()}\par
Discard \texttt{current}. If it was analysed, remove its Attempt from the
session so that only the new attempt is retained. Start a new prompted attempt
for the same item with independent support and return its Prompt (FR-SM2).
\item[] \texttt{skipAttempt()}\par
Discard \texttt{current} as in \texttt{repeatAttempt}. Retain no Attempt for it
and set \texttt{current} to absent.
\item[] \texttt{overrideAttempt(attemptId, correction)}\par
Raise \texttt{Missing} if the identifier is not among the session's attempts.
Raise \texttt{Invalid} if the correction does not name the actor's SLP identity
or names a phoneme-level change for an observation that does not exist.
Attach the correction to the Attempt. The original analysis is not changed
(FR-SM4 and FR-DMR3). A new correction for the same attempt replaces the
previous one.
\item[] \texttt{getSnapshot()}\par
Return a copy of the Session with its current attempts. The Session's status is
active.
\item[] \texttt{endSession()}\par
Discard \texttt{current} if it is prompted or flagged. Form the completed
snapshot: the session with status completed. Call
\texttt{saveSession(actor, snapshot)} of Patient Records \& Progress Tracking.
On success, set \texttt{session} and \texttt{current} to absent. On any
exception (\texttt{Denied}, \texttt{Invalid}, \texttt{Conflict}, or
\texttt{Unavailable}), propagate it and leave the session active and its
attempts unchanged, so that calling \texttt{endSession} again submits an
identical snapshot. A session with zero attempts may be ended and saved.
\end{description}

\subsubsection{Local Functions}
\texttt{allowedSupport(mode)} returns \{independent\} for Testing and
\{independent, semantic cue, repetition/model\} for Treatment.

\noindent The effective classification of an attempt is defined by
\texttt{effectiveResult} in the Dashboard (Section~\ref{mis:dashboard}) and by
\texttt{summarize} in Patient Records \& Progress Tracking
(Section~\ref{mis:records}). This module does not compute it. The Dashboard
treats a correct attempt as cued when its SupportLevel is semantic cue or
repetition/model.

\section{Audio Capture (\mref{mAudioCapture})} \label{mis:audio-capture}

\subsection{Module}

The Audio Capture module covers FR-AC1--3, FR-SM2, NFR-PER1, NFR-SAP2, and NFR-LAL1. Its purpose is to use an audio input adapter to capture audio, apply the necessary preprocessing, and persist recordings when required. The module may also perform lightweight validation and analysis to identify recording errors and report unusable audio.

\subsection{Uses}

The Audio Capture module uses the Audio Input Adapter module to access the currently registered audio input resource. It is responsible for managing the lifecycle of audio data, beginning with recording and ending when the audio is ready to be passed to the Speech Analysis module.

The module may perform several processing stages, including background noise reduction, input format normalization, resampling, and metadata generation. These stages ensure that recordings are in a suitable format for subsequent analysis.

The module also uses a persistence resource to store recordings when required. The SLP may configure whether raw audio is retained for the duration of a patient's visitation cycle, the current session, or not retained permanently at all. Regardless of the persistence setting, recordings are temporarily cached so that they can be referenced throughout the current session.

\subsection{Syntax}

The module also provides a recording status indicating whether a recording was successfully captured and processed. If a failure occurs during recording, validation, or processing, the appropriate exception is raised.

The resulting recording is made available to the Speech Analysis module through its recording reference. If permanent storage is enabled, the reference may also identify the persisted recording.

None.

\subsubsection{State Variables}

The module maintains the following state variables


\begin{itemize}
    \item A recording status indicating the current state of the module. Possible states include \texttt{Idle}, \texttt{Recording}, \texttt{Paused}, and \texttt{Processing}.
    \item A recording buffer used to temporarily store audio data while a recording is in progress.
    \item A reference to the most recently completed and validated recording, allowing it to be cached and accessed before being passed to the Speech Analysis module or permanently persisted.
\end{itemize}

The module may also maintain references to recordings cached during the current session. However, the Session Manager is responsible for maintaining the association between recordings and their corresponding session data.

\subsubsection{Environment Variables}

The primary environment variable used by this module is the registered audio input adapter supplied by the Audio Input Adapter module. This provides access to the microphone, file system, or other supported audio input resource.

The module also relies on the following environmental information:

\begin{itemize}
    \item Available storage space, to determine whether recordings can be cached or permanently persisted.
    \item Recording configuration, including sample rate, encoding, and supported audio formats.
    \item Persistence configuration, determining whether recordings should be retained for the current session, visitation cycle, or not permanently stored.
\end{itemize}

These variables influence how recordings are captured, processed, and stored.

\subsubsection{Assumptions}

\begin{enumerate}
    \item Exactly one recording may be in progress at a time.
    \item The system has successfully registered with a valid Audio Input Adapter and obtained the necessary permissions before recording begins.
    \item The registered audio input adapter remains available throughout the recording lifecycle.
    \item The Speech Analysis module has access to validated recordings produced by this module through their corresponding recording references.
    \item The system provides sufficient temporary memory to cache recordings during the current session.
    \item The recording configuration specifies a supported output format suitable for subsequent speech analysis.
\end{enumerate}

\subsubsection{Access Routine Semantics}

The Audio Capture module exposes operations that allow the Session Manager to control when audio recording begins, pauses, resumes, and ends. The Session Manager may use these operations to support different recording workflows.

For example, the SLP may choose to record continuously throughout a session, start and stop recording around individual target words, or temporarily pause recording while providing instructions or hints to the child.

\begin{description}

\item[] \texttt{startRecording}\par
Initialize the audio recorder and begin capturing audio from the currently registered audio input adapter. Set the module's recording status to \texttt{Recording} and initialize the recording buffer. If the module is not in a valid state to begin recording, or if the audio input resource cannot be accessed, raise \texttt{RecordingFailed}.

\item[] \texttt{stopRecording}\par
Stop capturing audio and finalize the current recording buffer. Set the recording status to \texttt{Processing} and execute the internal validation, caching, and preprocessing pipeline. Once processing is complete, store a reference to the resulting recording as the most recent recording and return its unique recording identifier. If the recording cannot be finalized, validated, or processed, raise \texttt{RecordingFailed}.

\item[] \texttt{pauseRecording}\par
Temporarily suspend audio capture while preserving the current recording buffer. Set the recording status to \texttt{Paused}. The recording may subsequently be continued using \texttt{resumeRecording()}. If no recording is currently in progress or the underlying audio resource cannot be paused, raise \texttt{RecordingFailed}.

\item[] \texttt{resumeRecording}\par
Resume audio capture using the existing recording buffer. Set the recording status to \texttt{Recording} and continue appending audio data to the current recording. If the module is not currently in the \texttt{Paused} state or the audio input resource cannot resume capture, raise \texttt{RecordingFailed}.

\item[] \texttt{saveMostRecentRecording}\par
Persist the most recently completed and validated recording using the configured persistence settings. Return the unique recording identifier associated with the persisted recording. If no completed recording is available, or if persistence fails, raise \texttt{RecordingFailed} or \texttt{Unavailable}, respectively. The operation does not modify the original recording or its processed contents.

\end{description}

The module may additionally support configurable automation, including automatically saving a recording when recording is stopped and automatically extracting relevant audio clips from a longer recording. These behaviours are controlled internally and do not require additional external access programs.

\subsubsection{Local Functions}

The following local functions are used internally to manage the recording lifecycle and prepare audio data for the Speech Analysis module.

\begin{description}

\item[] \texttt{validateRecording}\par
Perform lightweight validation to ensure that the captured audio is non-empty, uncorrupted, sufficiently clear, and in a supported format. If the recording fails validation, raise an appropriate recording validation exception so that the system can report that the audio is unusable.

\item[] \texttt{cacheRecording}\par
Temporarily store a validated recording in session-accessible memory. This ensures that the recording remains available for reference and subsequent processing throughout the current session, regardless of whether permanent persistence is enabled.

\item[] \texttt{preprocessRecording}\par
Apply the necessary preprocessing operations to prepare the audio for speech analysis. These operations may include background noise reduction, audio normalization, resampling, and input format conversion. Return the resulting processed recording.

\item[] \texttt{initializeRecorder}\par
Configure and initialize the audio recorder using the currently registered audio input adapter and the configured recording parameters. Ensure that the module is in a valid state to begin capturing audio.

\item[] \texttt{releaseRecorder}\par
Release the resources associated with the active audio recorder when recording is no longer required. Ensure that the module returns to the \texttt{Idle} state and that unnecessary hardware resources are no longer held.

\item[] \texttt{postprocessRecording}\par
Perform the final processing steps after a recording has been captured and validated. This function acts as an umbrella routine for generating recording metadata, assigning a unique recording identifier, updating the most recent recording reference, and persisting the recording when required by the configured settings.

\end{description}

Append a view event and return the
patient record.
\item[] \texttt{deletePatient(actor, patientId, confirmed)}\par
Raise
\texttt{Unconfirmed} if the SLP has not confirmed deletion for that patient.
Otherwise remove the patient, sessions, and attempts from active records in

\item[] \texttt{saveSession(actor, session)}\par
Validate completion, unique attempt

\item[] \texttt{getHistory(actor, patientId)}\par
Append a view event and return

Append an export event and

\item[] \texttt{getProgress(actor, patientId, target, pair)}\par

\item[] \texttt{getAudit(actor, patientRef)} and \texttt{copyAudit(actor, patientRef)}\par
Return matching events in append order or a copy of them. Include retained

\end{description}

\subsubsection{Local Functions}
\texttt{summarize(history, target)} reports per-session target counts and
support levels. Use phoneme-level corrections where present. Count accepted
productions as correct and substitutions or omissions as incorrect. Exclude
additions and unresolved unclassifiable occurrences. Attempt-level overrides
leave phoneme counts unchanged.

The correct rate is correct divided by eligible occurrences. Compare sessions
as follow-up minus baseline. Use the two latest eligible sessions for trends:
a higher rate indicates improvement, and errors in both indicate persistence.
Fewer than two eligible sessions yields no comparison or trend.

\section{Speech Analysis (\mref{mSpeechAnalysis})} \label{mis:analysis}

\subsection{Module}
Abstract object SpeechAnalysis. One instance converts a recorded attempt into
a phoneme-level analysis (FR-SA1, FR-RDV2--3, and FR-HA3). The analysis is
assistive only and does not replace the judgment of the SLP.

\subsection{Uses}
None. Session Management (\mref{mSessionManagement}) supplies the recording
captured through Audio Capture (\mref{mAudioCapture}). The module relies on a
pre-trained phoneme recognition model and the PanPhon feature table, which are
external to PronouncedFish.

\subsection{Syntax}

\subsubsection{Exported Types}
\begin{description}
\item[ModelConfig] Identifies the phoneme recognition model and the minimum
confidence below which a recognized phoneme is treated as unreliable.
\item[Recording] Audio of one attempt in the format fixed by Audio Capture.
\item[PracticeItem] One or more words. Each word has an expected IPA sequence
and a set of acceptable variant pronunciations. The practice item and target
phonemes are the same as those in Attempt
(Section~\ref{sec:interface-types}).
\item[Placement] One of initial, medial, or final: the position of an expected
phoneme within its word.
\item[Analysis] The original analysis of an Attempt
(Section~\ref{sec:interface-types}): expected and recognized IPA sequences, an
ordered sequence of SpeechError, confidence when available, aligned
observations, and classification.
\end{description}

\subsubsection{Exported Constants}
None.

\subsubsection{Exported Access Programs}
\noindent\begin{tabularx}{\textwidth}{@{}l X X l@{}}
\toprule
\textbf{Name} & \textbf{In} & \textbf{Out} & \textbf{Exceptions}\\
\midrule
\texttt{initialize} & ModelConfig & -- & Unavailable\\
\texttt{analyze} & Recording, PracticeItem & Analysis & Unavailable, Invalid\\
\texttt{placement} & Word length in $\mathbb{N}$, position in $\mathbb{N}$ &
Placement & Invalid\\
\texttt{phonemeDistance} & Expected phoneme, produced phoneme &
$\mathbb{N}$ or absent & Unavailable\\
\bottomrule
\end{tabularx}

\subsection{Semantics}

\subsubsection{State Variables}
An initialization flag, initially false, and the loaded recognition model and
feature table after initialization. No patient data is retained between calls.

\subsubsection{Environment Variables}
The model files and the PanPhon feature table, read during
\texttt{initialize}.

\subsubsection{Assumptions}
The recording was captured through Audio Capture in the agreed format. Each
word of the practice item has a non-empty expected IPA sequence. Recognized
phonemes are IPA symbols. Calls to \texttt{analyze} are independent.

\subsubsection{Access Routine Semantics}
Every operation except \texttt{initialize} and \texttt{placement} raises
\texttt{Unavailable} when the module has not been initialized or the model
fails.

\begin{description}
\item[] \texttt{initialize(config)}\par
Load the model and the PanPhon feature table, and set the initialization flag
on success. On failure, raise \texttt{Unavailable}.
\item[] \texttt{analyze(recording, item)}\par
Raise \texttt{Invalid} if the recording cannot be decoded or the item has no
expected phonemes. Otherwise:
\begin{enumerate}
\item Recognize the phoneme sequence in the recording, with a confidence value
for each recognized phoneme when the model provides one.
\item If no phonemes are recognized, or every recognized phoneme falls below
the minimum confidence, return an analysis with absent recognized IPA, no
SpeechError, every observation unclassifiable, and an unclassifiable
classification. This is not an exception.
\item Otherwise, for each word apply \texttt{align} between the recognized
sequence and the expected sequence and each acceptable variant. Use the
alignment of lowest cost, preferring the expected sequence on a tie.
\item Produce one observation for each target occurrence. A pair of identical
phonemes is accepted, a pair of different phonemes is incorrect, and an
expected phoneme with no counterpart is incorrect with an absent produced
phoneme. Additions are not target occurrences and produce no observation.
\item Create one SpeechError per difference: a Substitution for a pair of
different phonemes, an Omission for an expected phoneme with no counterpart,
and an Addition for a recognized phoneme with no counterpart. Record the
expected position of each Substitution and Omission and the insertion location
of each Addition. Order errors by word occurrence and position.
\item Classify the attempt as correct when no SpeechError exists and as
incorrect otherwise.
\end{enumerate}
The result is the original machine analysis. SLP corrections and overrides are
applied by Session Management and never change it.
\item[] \texttt{placement(length, position)}\par
Raise \texttt{Invalid} unless $1 \le position \le length$. Return initial if
$position = 1$, final if $position = length$ and $length > 1$, and medial
otherwise.
\item[] \texttt{phonemeDistance(expected, produced)}\par
Return $\sum_{i=1}^{n}|A_i-B_i|$ where $A$ and $B$ are the PanPhon feature
vectors of the two phonemes (the Manhattan distance). Return absent if either
phoneme has no feature vector.
\end{description}

\subsubsection{Local Functions}
\texttt{align(expected, recognized)} returns an alignment of two phoneme
sequences into pairs, omissions, and additions with minimum total cost. A pair
costs \texttt{phonemeDistance} of its phonemes. An omission or addition costs a
constant gap cost no smaller than the greatest possible pair distance. A pair
with an absent distance costs the gap cost. Ties are broken deterministically,
preferring pairs over gaps and then the earliest alignment.

\noindent The Dashboard normalizes a distance to the closeness scale
$1 - \frac{distance}{2n}$ (Section~\ref{mis:dashboard}), so both modules use
the same SRS feature vectors, and recognition confidence is reported separately.

\section{Reflection}


Please note that we combined the MG and MIS into this one document so the reflection is based on our experiences for them both. We worked on them side by side, as the MIS just goes into some more detail for topics covered at a higher level in the MG. 

\begin{enumerate}
  \item What went well while writing this deliverable?

        The brainstorming process went very smoothly for this deliverable. Our group felt appropriately prepared with considered design solutions and sources of inspiration when decomposing modules. We have already begun working on the proof of concept and have some wireframe mock-ups that map out the features and views we are going to need for the final design. Using this as a reference, we brainstormed all the unique features we will include (both during or after capstone timeline), and got a rough idea of the architecture we would want to design as well. This made it really easy to decompose our system into modules. 

  \item What pain points did you experience during this deliverable, and how
    did you resolve them?

    During this deliverable, we struggled with the actual architecture design aspect before the module decomposition. Initially, we were just blindly trying to put together a combination of modules without a general brainstorming session. This made it hard to add in new modules and pigeonholed us into designs since we were only considering a select few parts of the workflow we already had mapped out. To remedy this, we transitioned to brainstorming (mentioned in the last question) where we just made a big list of all the features and potential improvements we would add in the future. This way, it allowed for us to come up with a more robust design considering a wider variety of possibilities. This helped us think beyond the main workflow and towards potential enhancements instead. 

  \item Which of your design decisions stemmed from speaking to your client(s)
  or a proxy (e.g. your peers, stakeholders, potential users)? For those that
  were not, why, and where did they come from?

        Almost all of our design decisions stemmed from our supervisor, who acts as a proxy to our clients (SLPs). Others were software decisions made through group discussions. We were told that most SLPs use iPads for their sessions, so it brought up the idea of the audio input adapter module, as future expansions would need some abstract adapter to interface with various OS or hardware. We determined that an audio capture module would be helpful as well in case any pre-processing was needed. We were also told that SLPs would love to have a replay feature that lets them play back recordings from a session, so a save feature may be integrated here too. For session management, patient management, practice items, and dashboard element modules, we conducted interviews with our stakeholders using wireframe sketches. These discussions inspired a need for related features, so we partitioned them into related, abstract modules. A big part of our design is the audio analysis portion so it was a common understanding between us and the supervisors that this was a necessary portion. This is essential so we could put other ML models, or analysis mechanisms in general, even if they are unrelated to SLP needs. For example, it leaves it open for accent coaches as well. 

  \item While creating the design doc, what parts of your other documents (e.g.
  requirements, hazard analysis, etc), it any, needed to be changed, and why?
  
      When creating the design document, we noticed a lot of outdated information that came as a result of changing scope as the project progressed. For example, we limited the inputs to be from iPads since that is what is used most often. In our architecture, we still considered this to be an abstract concept as outlined by the Audio Input Adapter Module. 
      
      In general, some of these design decisions did not have strong links to requirements and vaguely pointed at general ones. This is not good because requirements should be clear, not open to interpretation. For example, we revised how we navigated PHIPPA compliance as per insight from our stakeholder interviews. We were told that as long as the PHI data storage is being done on a local drive, it may still comply with PHIPPA if done correctly. Our demonstrations also revealed that the SLPs were very excited by the idea of playing back voice clips or saving them to monitor progression over time. However the specifics of this are not communicated effectively in the SRS. An issue has been opened for this matter. 


  \item What are the limitations of your solution?  Put another way, given
  unlimited resources, what could you do to make the project better? (LO\_ProbSolutions)
  
  Given unlimited resources, our solution would remove a lot of the configurability within the design. For example, instead of letting the SLP choose to automatically clip audio files for them, this would be on by default. However our model is unlikely to be good enough for this to work properly, so it is a stretch feature in trial. Ideally, this would be what happens regularly and the SLP could just start and stop the recording once with no need for manual intervention. 

  Another limitation is with the variety of lesson plans that we can offer. Our current plan is to give one type of lesson plan: showing images and having the child repeat the word. This is done in a similar manner to how the standardized testing is done. But to give more personalized feedback, a very powerful model would be needed, and a greater variety of tests would need to be supported. The current design is trained for and suited to only single word, picture naming sessions. 

  
  \item Give a brief overview of other design solutions you considered.  What
  are the benefits and tradeoffs of those other designs compared with the chosen
  design?  From all the potential options, why did you select the documented design?
  (LO\_Explores)

  Some other design elements we considered were to combine the input adapter and input processing modules into one large block. This would simplify our implementation and reduce dependencies between modules. For our timeline, we only plan to support iPads so this would make it much easier for us. However, we decided against this in the long term, our design would like to support more devices and platforms. Furthermore, it is key to abstract out the analysis module because the input adapter and processing module can be reused generally for any speech task (adult SLP, accent coach). However our child SLP model is tailored for this one use case, so it would be a bad design to couple the analysis module with the input module. 

  Another design decision we considered was to completely separate the testing modules from the lesson plan modules. This was because the goal of testing is different to what is done during treatment. In testing, no hints or cues are provided, whereas treatment has a clearer focus. However, we decided against this because of the reusability possible between the two modules. Both testing and lessons could be implemented as an extension of a session. They might have the same structure but reveal different amounts of information to the child. Therefore, this behaviour was instead separated using the state pattern. This way their respective behaviours could be accommodated without needing redundant classes that hurt maintainability. 


  \item (After you have implemented another team's module, which means this
  isn't filled in until after the original deadline). What did you learn by
  implementing another team's module? Were all the details you needed in the
