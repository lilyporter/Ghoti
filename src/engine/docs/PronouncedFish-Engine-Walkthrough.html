Understanding the
recognition engine

How a local recording becomes a sequence of speech sounds—and how that capability fits into the application.

Working Python baseline

The engine uses a pretrained phonetic speech model to estimate the sounds produced in a recording. Our code prepares audio, executes the model locally, decodes its predictions, and returns a reusable structured result.

01 · PrepareLocal WAV/FLAC → mono waveform at 16 kHz
02 · RecognizePasketti / WavLM → symbol scores across time
03 · DecodeCTC decoding → IPA phone tokens and review status

Implemented: real Python inference, local audio preprocessing, phone tokenization, a CLI, and 35 passing software checks.

Next: target-based pronunciation analysis, evaluation on the intended child population, and browser/iPad inference. Source folders will be added when those features are implemented.

01 · The problem we are solving

Recognize the produced sounds

Recognition estimates what is in the audio. Pronunciation analysis compares that estimate with an intended target.

Phoneme

An intended contrastive sound category. For “rabbit,” the target begins with /ɹ/.

Phone

The actual produced sound. A child might produce [w], giving a production resembling “wabbit.”

Two questions, two components

QuestionResponsible component
What sounds appear in this recording?Acoustic recognition—implemented in Python.
How do those sounds differ from the target?Pronunciation analysis—not implemented yet.

The recognition API receives audio alone, with no expected word or expected IPA:

result = recognizer.recognize(audio)

This prevents application code from copying the target pronunciation into the recognition result. A learned recognizer can still mishear sounds or favor familiar productions. Whether it preserves a particular child's substitution correctly must be evaluated.

Where the learned ability comes from

We use Pasketti Phonetic, a published WavLM-based model fine-tuned to produce IPA from children's speech. Its trained weights supply the learned acoustic behavior; our package supplies the surrounding pipeline and integration boundary. [1]

ActivityWhat happens?Project status
Training / fine-tuningExamples and human references update model weights.No project-specific fine-tuning yet.
InferenceFixed trained weights process new audio.Implemented and exercised locally.

A recording does not train the model. Weights stay fixed during inference. The engine does not automatically collect recordings for retraining.

02 · What gets loaded

The model is a set of cooperating files

The architecture, learned weights, vocabulary, and preprocessing settings must agree with one another.

FileRole
model.safetensorsTrained numerical weights; about 1.26 GB on disk.
config.jsonHow to construct the network so the weights fit correctly.
vocab.jsonOutput ID → symbol mappings, such as 39 → ɹ.
preprocessor_config.jsonRequired sample rate, normalization, and processor settings.
tokenizer_config.jsonDecoding behavior, including blank and word-separator symbols.
special_tokens_map.jsonIdentifies special tokenizer symbols.
added_tokens.jsonAdditional tokenizer entry: currently <unk>.
pronouncedfish-model.jsonOur pinned revision and checksums for the model files.

The pinned model has about 315.5 million parameters. Its config specifies 24 transformer layers, 16 attention heads, a hidden size of 1,024, and an active recognition vocabulary size of 55.

Configuration is not learned knowledge. The config describes the network; the weights contain its learned numbers. Editing the config does not improve recognition and can make the checkpoint incompatible.

Constructing a recognizer

recognizer = PaskettiRecognizer("models/pasketti-phonetic")

The constructor verifies the local snapshot and checksums, loads the processor, constructs WavLM, loads its weights, rejects incomplete checkpoint loads, and places the model in evaluation mode on CPU or the requested CUDA device.

A checksum is a fingerprint of file contents. It helps detect changed or corrupted files. The pinned revision identifies exactly which model produced a result.

Wav2Vec2Processor is the expected processor class for this WavLMForCTC model. They share audio-processing and tokenizer machinery. [2]

The model runs in FP32. The publisher warns that half-precision WavLM calculations can produce non-finite values; reduced-precision deployment needs separate validation.

03 · Audio preparation and inference

A recording starts as numbers

A waveform is a sequence of signal samples, for example [0.001, 0.004, -0.002, …]. These values represent the recorded signal; they have not yet been assigned sound labels.

1

Read and validate. load_audio() accepts a local WAV or FLAC, checks that it is nonempty and at most 30 seconds, and rejects non-finite or out-of-range PCM values.

2

Convert to mono. Multiple channels are averaged. A stereo sample becomes (left + right) / 2.

3

Resample to 16 kHz. SoXR HQ produces 16,000 samples per second while preserving duration. Changing the sample-rate label alone would not perform the conversion.

4

Normalize and create a tensor. The processor applies its configured waveform normalization and creates a PyTorch numerical array for inference.

normalized sample ≈ (sample − waveform mean)
                    / waveform standard deviation

Normalization gives the model a consistent numerical scale. It does not remove noise or assess pronunciation quality.

Inside the neural network

Convolutional layers turn the waveform into a shorter sequence of learned acoustic representations. Transformer layers let those representations use surrounding audio as context. A classification head scores possible symbols at each output time step.

StageExample shapeMeaning
Waveform[1, 36226]One recording with about 36,226 samples.
Contextual features[1, 112, 1024]About 112 time steps, with 1,024 learned values each.
Output logits[1, 112, 55]Scores for 55 possible symbols at each step.

Shapes illustrate the roughly 2.26-second synthetic sample and pinned architecture. Other durations produce different numbers of time steps. A tensor is a numerical array with a defined shape.

Logits are raw scores. A larger score makes a symbol more competitive at a time step. The scores are not calibrated probabilities of transcription correctness.

04 · CTC decoding and tokenization

Many time steps become a few sounds

CTC stands for Connectionist Temporal Classification. A sound can span multiple time steps, so the model can predict a symbol repeatedly. It can also emit a special CTC blank. We use greedy decoding: select the highest-scoring symbol at each step, then let the CTC tokenizer collapse the sequence.

frame_ids = logits.argmax(dim=-1)
transcription = processor.batch_decode(frame_ids)[0]

Illustrative CTC sequence

Winning labels across time

blank · ɹ · ɹ · blank · æ · æ · blank · b · b · ɪ · ɪ · t · t

Collapse consecutive repetitions, then remove blanks

ɹ æ b ɪ t

Blank is a “no label emitted here” alignment symbol; it does not necessarily mean silence. Blank-separated repeats survive: t t blank t t becomes two t tokens.

A word-separator symbol becomes spaces in the transcription. Those boundaries are predictions too. The current implementation does not return validated phone timestamps.

A phone is not always one Unicode character

For later comparison, our model-specific parser groups phonetic marks into complete units:

RepresentationToken interpretation
ɹOne simple sound symbol.
ʧOne affricate in this model's spelling convention.
ẽOne token: a vowel plus its nasalization mark.
e͡iOne token containing explicitly tied sounds.

Untied adjacent vowels remain separate. Word spaces are preserved in the raw transcription but excluded from the phone list. Unsupported or malformed marks make a result unassessable while retaining the raw transcription for review.

The 55 output classes are symbols, not 55 English phonemes. They include blank, a word separator, sound symbols, and marks. The added tokenizer entry <unk> is outside the model's 55 output classes.

A prediction with explicit review status

The display-friendly string preserves word spaces; the phone list gives later algorithms complete sound units. This excerpt uses the observed synthetic phrase; the full result also includes the exact model revision and timing.

  "status": "ok",
  "recognized_phones": [
    "ð", "ə", "ɹ", "æ", "b", "ɪ", "t", "s", "ɪ",
    "t", "s", "ɪ", "n", "ð", "ə", "s", "ʌ", "n"
  ],
  "phonetic_transcription": "ðə ɹæbɪt sɪts ɪn ðə sʌn",
  "confidence_status": "uncalibrated",
  "requires_review": true
}
FieldMeaning
statusok: nonempty, parseable phones were produced. unassessable: input/output could not be used under the current checks.
recognized_phonesEstimated produced sounds, grouped into complete tokens.
phonetic_transcriptionDecoded IPA, including predicted word spaces.
model_versionModel identity and exact pinned revision.
inference_time_msNeural-network execution time; null if inference did not run.
confidence_statusuncalibrated after inference; unavailable if inference did not run.
requires_reviewCurrently true for every result; not a learned confidence-threshold decision.
review_reasonExplains the general review requirement or a specific unusable result.

“ok” establishes successful execution, not transcription accuracy. A plausible-looking sequence may still be wrong. Numeric correctness probabilities are not reported because calibration has not been established.

The recognizer flags extremely short, overly long, or near-silent input; non-finite scores; empty decodes; and malformed IPA. Invalid sample rate, buffer shape, or PCM values raise errors. Background noise, clipping within PCM bounds, and overlapping speakers need more complete quality handling.

06 · Understanding timing

Load once, recognize many attempts

The CLI starts a new process and constructs a new model on every invocation. An application should retain its initialized recognizer and reuse it:

from pronouncedfish_engine import PaskettiRecognizer, load_audio

# Once at development-application startup:
recognizer = PaskettiRecognizer("models/pasketti-phonetic")

def process_recording(path):
    return recognizer.recognize(load_audio(path))
TimingIncludes
model_load_msLibrary loading, asset checks, network construction, and loading weights.
preprocessing_msReading the file, channel conversion, and resampling.
inference_time_msThe neural-network forward pass.
processing_msFile preprocessing, input preparation, inference, validation, and decoding.

processing_ms already includes preprocessing and inference. Add model-load time to processing time for initialization plus processing; do not add all four fields together.

Recent fixes and local execution

Direct SoXR HQ resampling removed librosa's large first-call resampling overhead while preserving the waveform and output-length convention. Omitting a redundant mask for one unpadded utterance removed the mixed-mask warning; regression checks preserved the decoded result. CLI JSON now displays readable UTF-8 IPA.

download-model retrieves static assets from Hugging Face and accepts no audio. Recognition uses verified local files. The library does not upload audio, automatically persist recordings, or log transcriptions. The CLI intentionally prints results to the local terminal.

07 · How this fits into the app

Recognition and target analysis stay separate

The engine is a subproject under src/engine/. Future application code lives alongside it and consumes public interfaces. The engine does not depend on patient records, UI, authentication, or database code.

Future substitution-analysis example

Target word:          rabbit
Expected phonemes:    ["ɹ", "æ", "b", "ɪ", "t"]
Recognized phones:    ["w", "æ", "b", "ɪ", "t"]

Candidate: expected /ɹ/, produced [w], beginning

The analysis component will receive recognition, expected phonemes, SLP-approved acceptable variants, and an explicitly supported substitution inventory. It will align complete phone tokens and report supported candidates for review.

No analysis module is included yet. When implemented, alignment must preserve unsupported differences without treating them as validated clinical findings. Define its API alongside the working algorithm.

Browser work will be added when implemented

The repository currently contains only the working Python engine. The earlier browser types and placeholder analysis definitions were removed because they had no runtime or consumer. No empty future-feature folders are needed.

Browser deployment needs a compatible exported model, a local runtime such as ONNX Runtime Web, browser audio preparation, and validation on an actual iPad. Python and PyTorch are currently development tools; an inference server is not part of the planned production audio path.

Preserve original predictions when clinicians correct them. Future application code should retain provenance and pass corrected phones through analysis. Correction storage and provenance are not implemented yet.

08 · Working with the subproject

Run it, inspect it, then evaluate it

Run from src/engine/. New developers can first create the environment using conda env create -f environment.yml.

conda activate phoneme-engine
python -m pip install -e ".[dev]"

# Once per snapshot; about 1.26 GB of weights:
python -m pronouncedfish_engine download-model

# Authorized local development audio:
python -m pronouncedfish_engine recognize sample.wav

python -m pytest -q

Windows users can generate the synthetic fixture with scripts/New-SmokeAudio.ps1 (Microsoft David Desktop required). Model files are separate from the Python environment and can be reused across environments.

What the 35 passing checks establish

Checks cover audio validation/conversion, CTC decoding, phone grouping, and actual pretrained-model execution. Regression cases compare direct resampling with librosa and masked/unmasked decoding. The real-model check forbids network connections; it skips unless its model/audio environment variables are set.

Next evidence needed: human-annotated produced phones from the intended child population; token-level phone error rate and an agreed accuracy definition; substitution evaluation; confidence calibration; and iPad compatibility, memory, and latency testing. The SRS's 87% identification and under-10-second targets remain unverified.
