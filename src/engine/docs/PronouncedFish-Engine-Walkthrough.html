Recognition · Analysis · Frontend prototype

The engine uses a pretrained phonetic speech model to estimate the sounds produced in a recording. Our package prepares audio, runs the model locally, decodes complete phone tokens, and compares them against supplied targets. A standalone HTML prototype renders the analysis.

Implemented: local recognition, target analysis, experimental acoustic evidence, a frontend prototype, and 85 passing software checks.

Not established: intended-population accuracy, acoustic distortion detection, calibrated confidence, clinical severity, or iPad inference. The frontend is not connected to live recognition.

01 · The problem we are solving

Recognize the produced sounds

Recognition estimates what is in the audio. Pronunciation analysis compares that estimate with an intended target.

Phoneme

An intended contrastive sound category. For “rabbit,” the target begins with /ɹ/.

Phone

An individual speech sound. The recognizer estimates it from audio; a child might produce [w], giving a production resembling “wabbit.”

Two questions, two components

QuestionResponsible component
What sounds appear in this recording?Acoustic recognition—implemented in Python.
How do those sounds differ from the target?Target comparison—implemented in analysis.py; findings remain candidates.

The recognition API receives audio alone, with no expected word or expected IPA:

result = recognizer.recognize(audio)

This prevents application code from copying the target pronunciation into the recognition result. A learned recognizer can still mishear sounds or favor familiar productions. Whether it preserves a particular child's substitution correctly must be evaluated.

Where the learned ability comes from

We use Pasketti Phonetic, a published WavLM-based model fine-tuned to produce IPA from children's speech. Its trained weights supply the learned acoustic behavior; our package supplies the surrounding pipeline and integration boundary. [1]

ActivityWhat happens?Project status
Training / fine-tuningExamples and human references update model weights.No project-specific fine-tuning yet.
InferenceFixed trained weights process new audio.Implemented and exercised locally.

A recording does not train the model. Weights stay fixed during inference. The engine does not automatically collect recordings for retraining.

02 · What gets loaded

The model is a set of cooperating files

The architecture, learned weights, vocabulary, and preprocessing settings must agree with one another.

FileRole
model.safetensorsTrained numerical weights; about 1.26 GB on disk.
config.jsonHow to construct the network so the weights fit correctly.
vocab.jsonOutput ID → symbol mappings, such as 39 → ɹ.
preprocessor_config.jsonRequired sample rate, normalization, and processor settings.
tokenizer_config.jsonDecoding behavior, including blank and word-separator symbols.
special_tokens_map.jsonIdentifies special tokenizer symbols.
added_tokens.jsonAdditional tokenizer entry: currently <unk>.
pronouncedfish-model.jsonOur pinned revision and checksums for the model files.

The pinned model has about 315.5 million parameters. Its config specifies 24 transformer layers, 16 attention heads, a hidden size of 1,024, and an active recognition vocabulary size of 55.

Configuration is not learned knowledge. The config describes the network; the weights contain its learned numbers. Editing the config does not improve recognition and can make the checkpoint incompatible.

Constructing a recognizer

recognizer = PaskettiRecognizer("models/pasketti-phonetic")

The constructor verifies the local snapshot and checksums, loads the processor, constructs WavLM, loads its weights, rejects incomplete checkpoint loads, and places the model in evaluation mode on CPU or the requested CUDA device.

A checksum is a fingerprint of file contents. It helps detect changed or corrupted files. The pinned revision identifies exactly which model produced a result.

Wav2Vec2Processor is the expected processor class for this WavLMForCTC model. They share audio-processing and tokenizer machinery. [2]

The model runs in FP32. The publisher warns that half-precision WavLM calculations can produce non-finite values; reduced-precision deployment needs separate validation.

03 · Audio preparation and inference

A recording starts as numbers

A waveform is a sequence of signal samples, for example [0.001, 0.004, -0.002, …]. These values represent the recorded signal; they have not yet been assigned sound labels.

1

Read and validate. load_audio() accepts a local WAV or FLAC, checks that it is nonempty and at most 30 seconds, and rejects non-finite or out-of-range PCM values.

2

Convert to mono. Multiple channels are averaged. A stereo sample becomes (left + right) / 2.

3

Resample to 16 kHz. SoXR HQ produces 16,000 samples per second while preserving duration. Changing the sample-rate label alone would not perform the conversion.

4

Normalize and create a tensor. The processor applies its configured waveform normalization and creates a PyTorch numerical array for inference.

normalized sample ≈ (sample − waveform mean)
                    / waveform standard deviation

Normalization gives the model a consistent numerical scale. It does not remove noise or assess pronunciation quality.

Inside the neural network

Convolutional layers turn the waveform into a shorter sequence of learned acoustic representations. Transformer layers let those representations use surrounding audio as context. A classification head scores possible symbols at each output time step.

StageExample shapeMeaning
Waveform[1, 36226]One recording with about 36,226 samples.
Contextual features[1, 112, 1024]About 112 time steps, with 1,024 learned values each.
Output logits[1, 112, 55]Scores for 55 possible symbols at each step.

Shapes illustrate the roughly 2.26-second synthetic sample and pinned architecture. Other durations produce different numbers of time steps. A tensor is a numerical array with a defined shape.

Logits are raw scores. A larger score makes a symbol more competitive at a time step. The scores are not calibrated probabilities of transcription correctness.

04 · CTC decoding and tokenization

Many time steps become a few sounds

CTC stands for Connectionist Temporal Classification. A sound can span multiple time steps, so the model can predict a symbol repeatedly. It can also emit a special CTC blank. We use greedy decoding: select the highest-scoring symbol at each step, then let the CTC tokenizer collapse the sequence.

frame_ids = logits.argmax(dim=-1)
transcription = processor.batch_decode(frame_ids)[0]

Illustrative CTC sequence

Winning labels across time

blank · ɹ · ɹ · blank · æ · æ · blank · b · b · ɪ · ɪ · t · t

Collapse consecutive repetitions, then remove blanks

ɹ æ b ɪ t

Blank is a “no label emitted here” alignment symbol; it does not necessarily mean silence. Blank-separated repeats survive: t t blank t t becomes two t tokens.

A word-separator symbol becomes spaces in the transcription. Those boundaries are predictions too. The current implementation does not return validated phone timestamps.

A phone is not always one Unicode character

For later comparison, our model-specific parser groups phonetic marks into complete units:

RepresentationToken interpretation
ɹOne simple sound symbol.
ʧOne affricate in this model's spelling convention.
ẽOne token: a vowel plus its nasalization mark.
e͡iOne token containing explicitly tied sounds.

Untied adjacent vowels remain separate. Word spaces are preserved in the raw transcription but excluded from the phone list. Unsupported or malformed marks make a result unassessable while retaining the raw transcription for review.

The 55 output classes are symbols, not 55 English phonemes. They include blank, a word separator, sound symbols, and marks. The added tokenizer entry <unk> is outside the model's 55 output classes.

“ok” establishes successful execution, not transcription accuracy. A plausible-looking sequence may still be wrong. Numeric correctness probabilities are not reported because calibration has not been established.

The recognizer flags extremely short, overly long, or near-silent input; non-finite scores; empty decodes; and malformed IPA. Invalid sample rate, buffer shape, or PCM values raise errors. Background noise, clipping within PCM bounds, and overlapping speakers need more complete quality handling.

06 · Understanding timing

Load once, recognize many attempts

The CLI starts a new process and constructs a new model on every invocation. An application should retain its initialized recognizer and reuse it:

from pronouncedfish_engine import PaskettiRecognizer, load_audio

# Once at development-application startup:
recognizer = PaskettiRecognizer("models/pasketti-phonetic")

def process_recording(path):
    return recognizer.recognize(load_audio(path))
TimingIncludes
model_load_msLibrary loading, asset checks, network construction, and loading weights.
preprocessing_msReading the file, channel conversion, and resampling.
inference_time_msThe neural-network forward pass.
processing_msFile preprocessing, input preparation, inference, validation, and decoding.

Only inference_time_ms is in recognition JSON; the other timing values go to CLI stderr. processing_ms already includes preprocessing and inference. Add model-load time to processing time for initialization plus processing; do not add all four fields together.

Recent fixes and local execution

Direct SoXR HQ resampling removed librosa's large first-call resampling overhead while preserving the waveform and output-length convention. Omitting a redundant mask for one unpadded utterance removed the mixed-mask warning; regression checks preserved the decoded result. Interactive JSON displays IPA. Redirected JSON uses Unicode escapes so Windows PowerShell cannot corrupt the symbols.

download-model retrieves static assets from Hugging Face and accepts no audio. Recognition uses verified local files. The library does not upload audio, automatically persist recordings, or log transcriptions. The CLI intentionally prints results to the local terminal.

Phone pairs explain the comparison

Recognition asks what the model heard. Analysis compares that estimate with a supplied pronunciation.

comparison = analyze(
    recognition_result,
    expected_phones=["d", "ʌ", "k"],
    acceptable_variants=[],
    supported_substitutions=[],
)

For target “duck” and recognition resembling “tuck,” alignment produces one row per phone pair:

ExpectedRecognizedKind
dtCandidate substitution
ʌʌMatch
kkMatch

A phone pair is an alignment row, not an extra model. A gap has null on one side, displayed as ∅. Aligning sequences allows later sounds to match after an addition or omission. Indices count complete tokens, not characters, words, or milliseconds.

What SODA means here

CategoryCurrent behavior
SubstitutionDifferent aligned tokens. Inventory membership is supplied by the caller, directional, and false by default.
OmissionExpected token with no corresponding recognized token.
DistortionNot assessed. Symbol alignment does not establish acoustic quality.
AdditionRecognized token with no corresponding expected token.

Targets, variants, and spelling

The caller supplies the target and any acceptable complete pronunciations. Jiwer aligns complete phone tokens with unit edit costs. The engine selects the pronunciation with the fewest edits; ties prefer earlier variants. A matching acceptable variant does not become a substitution. Multiple equally minimal alignments may exist.

Comparison uses NFD normalization and spelling aliases g → ɡ, ʧ → t͡ʃ, and ʤ → d͡ʒ. Original spellings remain in output. Nasalization, length, and r versus ɹ remain distinct.

Candidate does not mean confirmed production error. A recognizer can mishear the child. SRS clinical substitution evaluation remains limited to an approved list; descriptive omissions/additions do not establish additional validated clinical scope.

How distance becomes a heatmap

The heatmap explains which encoded properties differ between two aligned sound categories.

For expected /d/ and recognized /t/, a few columns of the full vectors are:

Soundsylsonconsvoi
Expected d−1−1+1+1
Recognized t−1−1+1−1
Absolute difference0002
distance = Σ |expected_feature[i] − recognized_feature[i]|
         = 0 + 0 + … + |+1 − (−1)| + … + 0
         = 2

In the full 24-feature table, all other differences for this pair are zero. The raw Manhattan sum has no confidence or severity units.

Reading the frontend map

Aligned pairsylsonconsvoi
d → t0002
ʌ → ʌ0000
k → ∅————

Rows are phone pairs; columns are features; cells are absolute differences of 0, 1, or 2. The example above shows four columns only. A gap or unknown exact segment mapping has no vector comparison, rather than a fabricated zero distance. Tied sequences without a single entry are not silently split into several vectors.

Which kind of vector?

Used here: a symbolic 24-feature lookup based on the IPA label. Different concept: WavLM's learned 1,024-value representations across audio time steps. Comparing acoustic embeddings would need its own reference recordings, temporal alignment, and validation; it is not implemented.

A confusion matrix would count how often a target is recognized as each sound. That is different from a fixed sound-pair distance or this per-attempt feature map, and session aggregation is not implemented.

Zero distance does not prove correct articulation. A distorted sound can receive the same IPA label as the target. Recognizer errors also propagate into the feature comparison. Accepted variants are handled before interpreting candidate differences.

The SRS explicitly describes {−1, 0, +1} feature vectors, Manhattan distance, and FR-RDV5's heatmap. The current renderer demonstrates that symbolic calculation; clinical interpretation remains unvalidated.

Make a result file

From src/engine/, after generating sample.wav:

python -m pronouncedfish_engine recognize sample.wav > recognition.json
python -m pronouncedfish_engine analyze recognition.json --expected-phones ð ə ɹ æ b ɪ t s ɪ t s ɪ n ð ə s ʌ n > analysis.json

Use Open analysis JSON and select analysis.json. Recognition-only JSON receives an explanatory error because it contains no target comparison. The frontend supports UTF-8 and BOM-marked UTF-16. Example data is illustrative, not inferred from a child recording.

Page 15 adds the assess command, which returns recognition, analysis, and experimental acoustic evidence together. The demo renders raw log support and margins in a separate panel; these are not correctness percentages.

What is connected today?

The Python engine and HTML renderer are connected through saved files. There is no live HTTP endpoint, browser model runtime, microphone inference, patient/session database, authentication, or correction-history storage in this prototype. It makes no network requests and has no persistent session storage; explicit file downloads remain possible.

A future development application could call the Python engine through a backend and pass its result bundle into a view. A backend bridge would not satisfy a requirement for production inference entirely on the user's iPad; that requires a separately validated browser model/runtime.

Colors have an explicit legend. Alignment colors distinguish match/substitution/omission/addition. Heatmap colors encode feature differences. Neither color scheme is a validated clinical traffic-light score.

What the extra code adds

Pasketti supplies the learned recognition ability. The surrounding package supplies a reusable application boundary.

ConcernImplemented decision
Audio compatibilityLocal WAV/FLAC validation, mono conversion, direct SoXR HQ resampling, then model normalization.
RepeatabilityPinned revision and file hashes; explicit download; local-only model loading.
Usable outputComplete phone tokens, exact model identity, explicit unassessable/review states.
Target comparisonJiwer alignment and PanPhon data; no second trained model and no custom edit-distance implementation.
Frontend illustrationOne standalone HTML renderer rather than a framework or a new service.

Does this improve the underlying model?

No. Wrapping Pasketti does not improve its recognition accuracy. The code makes its input/output predictable, traceable, and useful for comparing practice items. Project-specific training, calibration, and population evaluation have not been performed.

What the official Pasketti demo already does

The publisher's Colab notebook presents child examples and a Jiwer comparison against human transcription of the same recording. Its legend uses yellow for model substitutions, red for missed sounds, and green for extra model sounds. Green does not mean correct child pronunciation.

ComparisonQuestion answered
Human produced-phone reference ↔ modelDid recognition transcribe this production accurately?
Practice target ↔ recognized phonesHow does the estimated production differ from an acceptable target?

A perfect transcription of “wabbit” can still differ from “rabbit.” The notebook does not implement PanPhon vector heatmaps. Its browser UI sends audio to the Colab kernel for inference; it is not evidence of on-device browser inference. Its separate word-recognition model is unnecessary for a known target supplied by our practice workflow.

Why there is no browser package or empty scaffold

Unused browser types and speculative folders were removed. One small EvidenceRecognizer boundary is now used by the acoustic workflow and replacement-model tests. Source lives in engine/pronouncedfish_engine/; the working demo is in engine/docs/. Downloaded config/tokenizer JSON files are required model assets. Ignored caches, generated metadata, and external conda libraries are not application modules.

Relevant tools: Jiwer alignment, PanPhon, and the Pasketti model card. Source code and model assets have separate licenses; see model-baseline.md.

Include real-weight inference in the tests

Current full run: 85 tests passed in 40.53 seconds. This includes real-model recognition and acoustic scoring with network connections blocked. Chrome checks exercised the frontend at desktop, tablet, and mobile widths. These checks establish software behavior, not clinical accuracy.

PowerShell and result files

--expected-phones is required because analysis needs a target. Redirected JSON uses Unicode escapes; JSON readers recover IPA. The analysis CLI detects UTF-8/16/32; the frontend handles UTF-8 and BOM-marked UTF-16. An old file whose IPA was corrupted during PowerShell redirection must be regenerated; converting its encoding alone cannot reconstruct the sounds.

CLI exit codes are 0 for an assessable result, 2 for unassessable, and 1 for execution errors. Missing required arguments are rejected by the argument parser. Timings/errors go to stderr; avoid merging them into a saved JSON result.

Remaining work and acceptance

Supply reviewed target items, acceptable variants, and an approved substitution inventory. Evaluate recognition and candidate differences on annotated speech from the intended population. Define accuracy/PER conventions and confidence calibration. Add recording/session/correction workflows; measure browser/iPad compatibility, memory, and latency. The SRS's 87% phoneme-identification and under-10-second targets remain unverified.

FR-SA3's numerical confidence threshold and FR-SA1's word-position labels are not implemented. Preserve original predictions when future clinician corrections are stored. Beyond the recognized phone label

The PanPhon map stays symbolic. A separate acoustic layer now evaluates the recording's CTC frame probabilities.

python -m pronouncedfish_engine assess sample.wav --expected-phones ð ə ɹ æ b ɪ t s ɪ t s ɪ n ð ə s ʌ n > assessment.json

One forward pass returns recognition, analysis, and acoustic_assessment. Existing command outputs are unchanged. The frontend displays and saves the bundle without running a model.

A restricted, explicit calculation

Replace each target phone with every declared candidate. Calculate full-sequence CTC probabilities, summing blank/repeat paths. Other target positions stay fixed; no segment boundary is assumed.

log_support[i] = log P_CTC(target | audio)
  − logsumexp_q log P_CTC(target with phone i replaced by q | audio)

log_margin[i] = log P_CTC(target | audio)
  − log P_CTC(target with phone i replaced by best alternative | audio)

The denominator includes the target; the best alternative excludes it. Support closer to zero means greater relative support. Positive margins favor the target; negative margins favor the alternative. Neither establishes correctness.

Our own model can fit this boundary

The app consumes results; a model adapter owns preprocessing, output classes, and decoding.

RecognitionRun(
    recognition=recognition_result,
    evidence=CTCEvidence(
        log_probs=frame_log_probabilities,  # time × classes
        phone_token_ids=complete_phone_to_native_id,
        blank_id=native_blank_id,
        model_version=recognition_result["model_version"],
        ignored_token_ids=word_separator_ids,
    ),
)

EvidenceRecognizer requires recognize_with_evidence(audio). The scoring module has no Pasketti numeric token IDs or hidden-vector dimensions. Another CTC model can provide its native mapping. A non-CTC model can supply evidence=None: recognition and symbolic comparison still work, while CTC scoring is unavailable.

This is one used interface with replacement-model tests, not a plugin registry or a training framework. Future non-CTC assessment would need its own named method and renderer support. Model, method, and calibration identity must travel with scores; scores and thresholds do not transfer automatically between models.
